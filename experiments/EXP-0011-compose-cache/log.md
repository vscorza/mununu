## Motivation

`Context::compose_named` (`crates/mununu-core/src/context/mod.rs:350`) rebuilds the product CLTS on every call. Mununu's DSL workflow is *evaluate N properties on the same composed automaton*; today every property pays the full BFS-product cost. `Context.cltss` is insert-only post-`ContextBuilder::finish` — there is no public API to mutate a registered CLTS — so `compose_named(a, b, mode)` is a pure function of `(a, b, mode)` and the result can be safely cached for the Context's lifetime.

Plan §B3 proposed:
- key the cache on `(left, right, mode)` precomputed `u64` hash;
- store the result as `Arc<Clts>` so cache hits are a refcount bump rather than a deep clone;
- guard against rare hash collisions by storing the full key and rechecking on hit.

Prior literature: Michie 1968 "Memo functions and machine learning" (CACM); the immutability argument is local to mununu's API and follows from `ContextBuilder` having no mutating methods.

## Hypothesis

≥10× wallclock improvement on multi-property DSL workflows where the same `(left, right, mode)` triple is composed repeatedly. (We expected something larger, but the steady-state cost of a hashmap lookup vs. a full BFS product is what we wanted Criterion to actually measure — pre-registered the conservative bound.)

## Method

- **Inputs.** Two 32-state random CLTSs generated by `RandomClts::new(seed).with_states(32).with_density(0.10).with_alphabet(3).with_uncontrollable_prefix(3)`. Seeds: `0xC0FFEE` for left, `0xDECAF` for right. The uncontrollable prefix is critical — it lets the two CLTSs share their (uncontrollable) alphabet without tripping `compose()`'s controllability validation, which gives us a real ~6 ms compose to measure rather than a fast-rejected error path.
- **Bench.** `crates/mununu-core/benches/composition_only.rs::bench_compose_cache`, two arms in the same Criterion group:
  - `uncached` calls `Context::compose_named(...)` (forces a rebuild every iteration).
  - `cached` calls `Context::compose_named_cached(...)` on a Context whose cache has already been warmed (Criterion's warmup populates it on the first iteration; the measured iterations are all hits).
  - Group config: `measurement_time = 20s`, `sample_size = 15`.
- **Test gate.** Full `cargo test -p mununu-core --features test_support` — 825 lib tests must stay green.
- **Statistical test.** Criterion's default median + 95% CI; the gap between arms is ~5 orders of magnitude, so significance testing is moot — the hypothesis would survive any reasonable bootstrap.

## Results

- **Median.**
  - uncached: 6.247 ms
  - cached: 46.23 ns
- **95% CI.**
  - uncached: [6.189, 6.316] ms
  - cached: [46.02, 49.07] ns
- **Speedup:** ≈135,132× (cache-hit cost is 7.4 ppm of cache-miss cost).
- **Memory.** Not directly measured in this EXP. The cache stores one `Arc<Clts>` per unique `(left, right, mode)` triple plus one `String` × 2 + `Discriminant` per entry. Typical Mununu workflows have O(10) compositions, so the cache footprint is bounded by O(10 × sizeof(Clts)).
- **Tests.** All 825 lib tests green with the collision-safe variant.

## Interpretation

Hypothesis held with ~four orders of magnitude to spare — the cache hit is essentially the cost of a hashmap probe + Arc refcount bump, and the cache miss is dominated by BFS product construction. The interesting subtleties were elsewhere:

1. **Cache key allocation matters.** The first cut keyed the HashMap on `(String, String, Discriminant)` directly. That requires `String::to_string()` × 2 on every lookup — two heap allocations per hit. Replacing with a precomputed `u64` hash via `DefaultHasher` and storing the full key alongside the `Arc<Clts>` for collision recheck dropped the cache-hit cost from ~110 ns to ~46 ns.
2. **Collision safety.** A naive `HashMap<u64, Arc<Clts>>` would silently return the wrong CLTS on a 1-in-2^64 hash collision. The implementation stores `(String, String, Discriminant, Arc<Clts>)` as the value and rechecks the full key on hit; on collision it falls through to the miss path. The recheck cost is dwarfed by the BFS cost on a true miss.
3. **Methodology bug discovered.** While building the bench I found that the existing `composition_only` benches (chain_1k × ring_1k, etc.) were measuring the error path — chain_1k and ring_1k share their controllable alphabet, and `compose()` rejects that. Switching to random CLTSs with `with_uncontrollable_prefix(3)` produced real compose timings. This invalidates the magnitudes (not the directions) of EXP-0010, EXP-0003, EXP-0030 — corrigenda notes added to those archives.

## Dead-ends

- **2026-05-07 — `(String, String, Discriminant)` cache key.** Allocations on every lookup made the hit path ~2.5× slower than necessary. Replaced with `u64` hash + full-key recheck.

## Followups

- **EXP-0011-witness.** Audit whether `compose_named_cached` is safe in the presence of `WitnessMap` extraction — the cache key doesn't include witness-extraction options, but those live on `EvaluationOptions` rather than `CompositionOptions`, so this should be fine. Confirm by inspection.
- **EXP-0011-corrigenda.** Append a corrigenda note to `EXP-0010-fxhash-composition`, `EXP-0003-labelset-interning`, and `EXP-0030-csr-adjacency` flagging that the `composition_only` bench fixtures were measuring the validation error path at the time those experiments ran. Magnitudes don't reflect real compose cost; the falsification *directions* still stand because they showed regressions on whatever path was being exercised.
- **EXP-0011-callers.** Replace `compose_named` callers (DSL evaluator, synthesis pipeline) with `compose_named_cached` so the DSL workflow gets the speedup automatically. Out of scope for this EXP.
