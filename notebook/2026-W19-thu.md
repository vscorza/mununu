### Regression-mitigation protocol (in response to user question mid-sitting)

Built a four-level protocol after the user asked whether we have a regression mechanism for cache differences across isolated runs. We didn't — Criterion's `--save-baseline` / `--baseline` plus `bench_diff.sh` >10% threshold gate handles per-process variance but does nothing about cross-process cache state.

- **Level 1 — smoke**: `cargo bench --quick`. Indicative only.
- **Level 2 — EXP record with warmup**: `scripts/bench_record.sh --fresh --warmup ...` runs once at `--quick` and discards before the real recording. New `--warmup` flag landed in this sitting.
- **Level 3 — same-session A/B**: new [`scripts/bench_compare.sh`](../scripts/bench_compare.sh) saves a baseline + records a candidate in the same shell session, keeping OS scheduler / thermal / mmap state constant.
- **Level 4 — dedicated runner**: in `mununu-dev` container, Turbo Boost off, core-pinned, with `scripts/bench_diff.sh --robust` (Mann-Whitney U test p<0.01 + median threshold) as the gate. Required for paper-grade evidence.

`bench_diff.sh` gained a `--robust` mode that reads Criterion's per-iteration `sample.json`, computes a Mann-Whitney U test p-value via normal approximation (no scipy dep), and demotes apparent regressions to neutral when p≥0.01. Demotes false positives from bimodal distributions caused by cache shifts or transient noise.

ADR-0006 records the protocol decision; [BENCH_POLICY.md](BENCH_POLICY.md) "Regression mitigation" carries the operator-facing details.

### Sitting 3, late afternoon — EXP-0002a re-run (in response to user question)

User asked: "do we have previous tests and benches re ran with warmup?" Answer: no. Ran the first L3-protocol A/B comparison (`scripts/bench_compare.sh`, warmup discard, same-session, full Criterion samples). Captured as [EXP-0002a-warmup-rerun](../experiments/EXP-0002a-warmup-rerun/).

**Headline corrected finding:**
- EXP-0002's apparent 5-7× speedup was **100% cache-warmup contamination**.
- Clean L3 A/B shows mu-fixpoints +10-27% slower with SoA (Criterion p<0.05 on chain/ring), nu-fixpoints −3-5% faster (p<0.05 on chain/ring), grid_32x32 indistinguishable.
- The mu_calculus_only benches don't exercise `iteration_ranks` (witness_map = None), so the observed differences are LLVM monomorphization noise — not a real HashMap-vs-SoA comparison.
- Original ≥2× hypothesis is **unaddressed** by either archive; needs a synthesis-bound bench to test on the right workload.

**Decisions:**
- **Keep the SoA migration**: it's a type-safer API, lays groundwork for EXP-0007, and the "regression" is on a workload it doesn't even hit. ADR-0007 records this.
- **EXP-0002 stays as historical evidence** of the contamination class with a SUPERSEDED banner. ADR-0004 "supersede, don't rewrite" applied.
- **EXP-0002b is required** before any blog/paper claim about the SoA's hot-path performance.

**Bug fixes from this sub-sitting:**
- `scripts/bench_compare.sh` failed under `set -u` with empty `CRITERION_ARGS`. Fixed via explicit empty-array checks.
- `scripts/new_experiment.sh` rejected `0002a` as malformed; relaxed regex to `^[0-9]{4}[a-z]?$` for re-run/follow-up suffixes.
- `--quick` produces only 2 samples per bench, far below Mann-Whitney's n≥8 threshold. The `--robust` significance gate skipped every bench in the first attempt; corrected by running without `--quick` for n=30.

The L3 protocol works as designed — the contamination was caught by the protocol, not despite it. Reproducibility contract (notebook/0000-overview.md) survives intact.
