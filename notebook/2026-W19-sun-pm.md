### Refined taxonomy

ADR-0014 generalizes the rule from "structural wins, drop-ins lose" to **"changes that reduce total work win; changes that add work lose."**

The four falsifications all add work:
- §B2 FxHashMap: same probes, different hasher (no work reduction).
- §A2 LabelSetTable: extra find probe before existing probe (+1 probe).
- §B4 track-during-merge: replaced fast primitive (memcpy + early-exit compare) with serial word-loop (more total ops).
- §A3 CSR-via-staging: added O(|E|) flatten on top of existing build (+1 full copy).

The two confirmations reduce work:
- §A1 SoA: lazy Vec init replaces HashMap allocation per call.
- §A4 Vec doubling: removed wrapper code; let std handle growth.

### Why §A3 might still win via redesign

The plan §A3 design (flat CSR) is sound; this implementation built CSR by **flattening an existing staging Vec<Vec<>>** which keeps both data structures alive momentarily and pays the copy cost.

A **from-scratch direct-CSR-build** would:
1. Pre-compute per-state outgoing counts (already done at clts/mod.rs:1881-1886).
2. Allocate flat `Vec<Transition>` with total capacity once.
3. Use a per-state cursor to push directly into `flat[cursor[from]++]`.

This eliminates the staging Vec<Vec<>> AND the flatten pass. The build-time cost matches the original (one Vec push per transition) and the consumer-side cache locality wins are retained.

Estimated effort: 2-3 hours additional refactor on top of EXP-0030. Schedule as EXP-0031-csr-direct-build if pursued.
