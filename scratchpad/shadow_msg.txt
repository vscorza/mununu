fix(btor2/shadow): decide `$past` over a primary input instead of skipping it

The SVA translator announces exactly which shadow registers a formula needs:

    required __past shadow registers: din(8), q_r(8)

and only one of them was built. `augment_with_past_shadows` resolved a base
through `resolve_state_by_symbol`, which finds state cells only, so a `$past`
over a primary input produced a formula referencing a name absent from the
model. Every engine then correctly reported

    skipped — predicate references unknown register/signal `din__past`

Two assertions, same file, same run, opposite outcomes — `q_r == $past(din)`
skipped, `q_r != $past(q_r)` decided. `grep -c din__past design.btor` returned 0.

WHY IT MATTERS. `$past` of an input is what every data-integrity property is
written over, because the antecedent samples an input:

    (push && !pop && cnt_q == 0) |=> (d0_q == $past(din))

That is the FIFO in every clock crossing, a DMA payload, a mailbox command
word. The only workaround was to add a non-functional shadow register to the
DESIGN and write the property over registers — exactly the "shadow-logic tax"
docs/design/recoverability-vs-sva.md criticises SVA workarounds for.

THE RESTRICTION WAS CONSERVATIVE, NOT SEMANTIC. `next` sourced from an `input`
node is well-formed BTOR2 with exactly the right meaning: the flop samples the
input at cycle t and presents it at t+1. Confirmed by hand-augmenting a model
and running it through the full portfolio, which accepted it unchanged.

ONE RULE, ONE PLACE. `verify_auto` pre-filters the requested bases before
calling the augmenter, and that filter asked `resolve_state_by_symbol`
independently. Teaching only the augmenter about inputs would leave the fix
INERT on the single path users take — input bases dropped before they ever
arrive — while every unit test passed, because unit tests call the augmenter
directly. So the predicate is now exported as `can_shadow` and the filter asks
it. Two independent answers to "what is a valid base" is how this stayed broken.

RESOLUTION IS EXACT BEFORE FUZZY. `resolve_state_by_symbol` also matches an
`op`/`output` line named `base` and walks its cone to the nearest state — a hit
at distance N. Asking it first would let that distant state outrank an `input`
line carrying the name exactly. `resolve_shadow_source` therefore tries a
unique exact state symbol, then an exact input symbol, then the cone walk; a
name held by two states falls through to the walk, which rejects the ambiguity
itself rather than picking one arbitrarily. The result is a `ShadowSource` enum
rather than a `(Nid, Nid, bool)` tuple, so the two NIDs cannot be swapped.

SOUNDNESS: an input's shadow is PINNED TO ZERO at cycle 0, and that is a stated
approximation rather than an exact model.

Leaving it free is the more faithful reading of SVA, where `$past` is undefined
before the first clock edge. It is not a choice this adapter can make. An
init-less BTOR2 state cell means different things to different engines: the cube
and exact engines default it to 0 (`state_cell_init_values` /
`initial_state_bdd`, per the `setundef -zero` power-up), while the reachability
portfolio leaves it FREE, per BTOR2's nondeterministic-init semantics. That is
precisely the verdict DISAGREEMENT `reset_init::inject_zero_init` exists to
close — and it cannot close this one, because it runs on the pre-augmentation
BTOR2, before the shadow is appended. A free shadow escapes the mitigation by
construction, so a portfolio run and an exact run would disagree on cycle 0.

The cost is bounded and named: at CYCLE 0 ONLY, an atom over an input shadow
reads `$past(din) == 0`, so `$stable`/`$rose`/`$fell` of an input are decided
there against an invented history and those cycle-0 verdicts do not transfer to
hardware. Every later cycle is exact — a real added flop, not an abstraction.

NID ORDER IS PART OF THE CONTRACT. btormc's parser requires an `init` value's
NID to be BELOW the state's, so the zero is allocated before the shadow flop
rather than beside its `init` line. mununu's own parser is order-agnostic, which
is exactly why this is worth a test: the wrong order reads fine in-process and is
rejected by the external oracle, surfacing as a portfolio failure rather than a
parse error. A state cell's shadow needs no such care — it reuses the source's
own value node, already far below.

TESTS. In the module: an input gets a flop sourced from the input node; that
shadow carries an explicit zero init, declared before the state it inits; an
exact input outranks a like-named alias over a distant state; a state cell still
wins a direct name collision.

And a new docker-gated `tests/past_shadow_input_e2e.rs` runs the FIFO-capture
shape all the way through `verify_auto` — the only level at which the pre-filter
is visible. Three claims: the property is DECIDED rather than skipped under the
default posture; the model actually gained the flop (state_register_count 2 for
a one-flop design, and `din__past` present in the translated formula); and a
contrast twin with the capture DROPPED does not come back `Holds`, which is the
gate a vacuous property fails.

The twin lands on `Unknown`, not `Violated`, and that is the honest ceiling. The
default posture is a may-only over-approximation: a definite HOLDS transfers to
the RTL, but refuting needs must-edges, and this violation is data-dependent.
1-bit data, `max_iterations` 64, and predicate hints on both `din` and
`din__past` were each tried; every one stays at ⊥. `exact_symbolic` refuses the
class outright, correctly — it leaves inputs free, so a formula pinning an input
would decouple antecedent from consequent, and it says so rather than guessing.

TWO PRE-EXISTING DEFECTS surfaced while writing that test. Neither is addressed
here and neither is introduced by input support — both reproduce identically on a
REGISTER-sourced `$past`, and a property with no `$past` is unaffected in both
postures, which points at one root cause: an appended shadow flop breaking the
KMTS `must ⊑ may` containment.

  * `symbolic_engine: true` over any `$past` model panics at
    `mu_calculus/symbolic.rs:179` — "TritBdd invariant must ⊑ may".
  * `must_edge_inference: SmtPerTarget` reports `Violated` for a CORRECT design
    carrying a `$past` property. A false positive, not an abstention.

They are recorded in the test module's header so the next reader does not
rediscover them.


Also relaxes `missing_base_is_an_error_not_silent`, which asserted the exact
error prose rather than its intent. The wording changed when inputs became valid
bases; the test now checks that the message names the signal and says it did not
resolve, which is what it was actually verifying.

Surface parity: not applicable. No CLI flag, API field or UI affordance is added
— this is a model-building fix beneath all three surfaces equally.
