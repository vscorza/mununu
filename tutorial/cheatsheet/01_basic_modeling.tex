\begin{cheatbox}{File Structure}
Every \code{.ctxdsl} file is wrapped in a single \code{context}:
\begin{lstlisting}[style=ctxdsl]
context my_system {
    alphabet { ... }
    automata { ... }
    mu_formulas { ... }
}
\end{lstlisting}
Sections can appear in any order.  One context per file.
\end{cheatbox}

\begin{cheatbox}{Alphabet}
Declares the set of observable events/signals:
\begin{lstlisting}[style=ctxdsl]
alphabet {
    label unlock;
    label lock;
    label bad_code;
}
\end{lstlisting}
Labels are global to the context.  If two automata share a label name, it becomes a \emph{synchronization point} during composition.
\end{cheatbox}

\begin{cheatbox}{Automaton}
A finite-state machine lives inside the \code{automata} block:
\begin{lstlisting}[style=ctxdsl]
automata {
    automaton DoorLock {
        states { ... }
        transitions { ... }
    }
}
\end{lstlisting}
You can define multiple automata in the same context.
\end{cheatbox}

%% ---- COLUMN 2 ----

\begin{cheatbox}{States}
Declare states inside the automaton.  Exactly one must be \code{initial}:
\begin{lstlisting}[style=ctxdsl]
states {
    state Locked initial;
    state Unlocked;
    state Strike1;
    state Lockout;
}
\end{lstlisting}
State names become predicates you can reference in mu-calculus formulas.
\end{cheatbox}

\begin{cheatbox}{Transitions}
Each transition connects two states on a label:
\begin{lstlisting}[style=ctxdsl]
transitions {
    transition Locked -> Unlocked
        on label unlock;
    transition Unlocked -> Locked
        on label lock;
    // Self-loop
    transition Locked -> Locked
        on label timeout;
}
\end{lstlisting}
A state with no outgoing transitions is a \emph{deadlock}.
\end{cheatbox}

\begin{tipbox}{State Predicates in Formulas}
State names double as atomic propositions.  You can write:
\begin{lstlisting}[style=ctxdsl]
body = mu X. (Lockout || <> X);
\end{lstlisting}
This checks reachability of the \code{Lockout} state.
\end{tipbox}

%% ---- COLUMN 3 ----

\begin{cheatbox}{Mu-Calculus Basics}
Formulas live in \code{mu\_formulas}.  Two fixpoints:

\smallskip
\begin{tabularx}{\linewidth}{@{}lX@{}}
\toprule
\code{nu X.~$\varphi$} & Greatest fixpoint (safety) \\
\code{mu X.~$\varphi$} & Least fixpoint (reachability) \\
\midrule
\code{[] $\varphi$} & Box --- all successors satisfy $\varphi$ \\
\code{<> $\varphi$} & Diamond --- some successor satisfies $\varphi$ \\
\bottomrule
\end{tabularx}

\smallskip
Common patterns:
\begin{lstlisting}[style=ctxdsl]
// Safety: always valid
nu X. ([] X)
// Reachability: target reachable
mu X. (Target || <> X)
\end{lstlisting}
\end{cheatbox}

\begin{cheatbox}{CLI Commands}
\begin{lstlisting}[style=shell]
# Evaluate a formula
mununu context eval file.ctxdsl \
    --formula safety_invariant \
    --automaton DoorLock

# Show context summary
mununu context summarize file.ctxdsl
\end{lstlisting}
\end{cheatbox}

\begin{tipbox}{First Steps}
Always start by checking \code{safety\_invariant} (\code{nu X.\ ([] X)}) to confirm your model has no unexpected deadlocks or missing transitions before writing complex properties.
\end{tipbox}
